# 自我反思與修正流程

## 目的
讓主持者與資料庫能從可觀察的錯誤中改善，而不是只宣稱「已經修好」。本流程不需要 AI API；GitHub Actions 負責可重現的機械檢查，AI 對話負責理解情境、提出假說與撰寫提案。

## 每次遊戲回合的主持者閉環
1. **理解**：確認玩家真正想做什麼；不把選單當成行動白名單。
2. **預檢**：檢查角色能力、知識、資源、時間、地點、NPC 在場理由與世界規則。
3. **執行**：依條件呈現成功、部分成功、代價、失敗或資訊不足，不為戲劇效果任意改判。
4. **更新**：同步時間、位置、物品、資源、傷勢、關係、知識、線索、承諾與事件因果。
5. **反思**：檢查是否忽略玩家意圖、讓 NPC 不合理知情、跳過成本、改變既定事實或遺漏存檔。
6. **修正**：若有錯誤，記錄根因與修正方案；不可只改敘述掩蓋狀態矛盾。
7. **回歸**：用原案例及反例重新測試，確認修正沒有破壞其他玩法。

## 錯誤分類
- **主持失誤**：本回合理解、判定、敘事或狀態更新錯誤；先修正本次存檔與主持流程。
- **資料錯誤**：百科、時間線、角色或規則文件內容錯誤；追查來源並標記可信度。
- **規則缺口**：現有規則沒有覆蓋該情況；提出新規則及邊界案例。
- **玩家偏好**：玩家希望改變節奏、難度或題材；優先作為本次模擬設定，不自動升級成全域規則。
- **工具／平台問題**：GitHub、網頁或對話工具失效；如實回報未完成，不偽稱已存檔。

## 修正提案必填
每個正式規則修正至少說明：
- 可重現的情境與實際結果
- 預期結果及玩家影響
- 根因（不是表面症狀）
- 修正內容與適用範圍
- 反例、濫用方式與可能副作用
- 回歸測試案例
- 回復舊版的方法

## 紅隊審查
修正者以外的審查步驟必須嘗試推翻提案：尋找矛盾、漏洞、玩家自由度退化、NPC 被工具化、狀態同步副作用及正典污染。若沒有真正獨立的人或 Agent 參與，報告必須明確標示為「自我紅隊」，不得冒稱外部審查。

## 權限與安全邊界
- GitHub Actions 只執行確定性檢查，不呼叫 AI API、不讀取玩家私人對話。
- AI 可以提出修改並編寫草案；正式規則變更必須經玩家／維護者人工核准。本流程不自動合併任何規則提案。
- 單次模擬內容預設只寫入該次存檔；不可把玩家角色、秘密或私人對話搬進 global。
- 不確定的原著資料標記「待核對」，不可為了通過測試而捏造來源。
- 重大世界狀態變更、不可逆劇情與跨模擬共用設定，須取得玩家確認。

## 完成定義
一個問題只有在「原因已說明、修正已提交、原案例通過、反例通過、回歸測試通過、影響範圍已記錄」後，才可標示為完成。若只完成其中部分，狀態必須寫成進行中或待驗證。
